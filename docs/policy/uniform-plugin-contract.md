This document is the canonical reference for contributors who need to add or change a uniform in the GMT shader pipeline. The contract today is **distributed across four contribution paths** (the BASE schema, two feature-side mechanisms harvested by `featureRegistry.getUniformDefinitions()`, and direct write-side registration in `UniformManager`), with no single in-source overview. Drift across these paths is real: the `backingOnly` flag is declared in one tree and enforced in another (`engine/UniformSchema.ts:35-42` vs `shaders/chunks/uniforms.ts:8`), and `UniformDefinition.comment` has no consumer at all. Uniform-name collisions used to be silent; since `36ad672c` they throw at module load (`engine/UniformSchema.ts:113-131`). This doc gives a decision tree per path, the must-hold invariants, and the known footguns so future shader-extension work has a citable single reference.

## Existing contribution paths (catalog)

Four paths contribute a uniform to the final GLSL `uniform …;` declarations and the Three.js `material.uniforms` map. All four feed the same downstream consumers (the static preamble producer at `shaders/chunks/uniforms.ts:7-14`, the schema-driven Three.js backing factory at `engine/UniformSchema.ts:141-155`, and the engine-gmt per-frame writer `UniformManager.syncFrame` at `engine-gmt/engine/managers/UniformManager.ts:112-525`).

## Rules for adding a new uniform

R1. **If the uniform is tied to a feature's params and changes per-frame from store state, use `params.<key>.uniform` (path 3).** Do NOT add it to `extraUniforms` and do NOT add it to `BASE_SCHEMA`. The DDFS routing in `store/createFeatureSlice.ts` already handles uniform emit, CONFIG-event diff, gradient-buffer texture path, and animation/undo/preset round-trip for path-3 uniforms; the other paths do not. Cite: `engine/FeatureSystem.ts:108-219` (ParamConfig), `engine/FeatureSystem.ts:691-710` (harvester branch).

R2. **If the uniform is an array, a sampler the feature owns, or needs `backingOnly: true`, use `extraUniforms` (path 2).** Path 3's auto-derivation does not carry `arraySize`; it never sets `backingOnly`; and `image`/`gradient` types route through dedicated texture channels rather than schema. Cite: `engine/FeatureSystem.ts:344-345`, `engine-gmt/features/lighting/index.ts:128-158`, `engine-gmt/features/core_math.ts:59-63`.

R3. **`BASE_SCHEMA` (path 1) is reserved for three sub-categories only:** true engine-core uniforms (camera/time/resolution); tool/export slots whose defaults are a no-op identity (bucket-render tile, histogram layer, multi-pass output); and CPU-derived caches of feature uniforms that multiple consumer features read with safe identity defaults (the two examples at `engine/UniformSchema.ts:100-101` are the precedent). Adding anything else to `BASE_SCHEMA` is a contract violation — see q-028 for the full rationale (`docs/history/doc-audit-state/survey/_followups/q-028.md`).

R4. **Engine-core uniforms with no GMT coupling go in `engine/UniformSchema.ts` BASE_SCHEMA; GMT-specific uniforms go via a feature in the engine-gmt tree.** The engine-core and engine-gmt copies of `UniformSchema.ts` are a Pattern C parametrisation-hook fork (see [`docs/policy/engine-fork-rules.md`](./engine-fork-rules.md)): the designed divergence is the import path of `registerFeatures()` (`engine/UniformSchema.ts:22` vs `engine-gmt/engine/UniformSchema.ts:5`), which composes a different sibling `features/` set per tree. Editing only one copy of the *shared* `BASE_SCHEMA` prefix will silently desync the two engines — keep that prefix identical or move the change into a path-2/path-3 feature. (GMT-only BASE entries have in fact accumulated in the engine-gmt copy; see I1.)

R5. **Avoid direct `UniformManager.update()` writes (path 4) for new uniforms unless the value is a CPU-derived per-frame cache of another uniform's value.** Direct writes bypass the schema-driven validation, the CONFIG-event diff in `engine-gmt/engine/managers/ConfigManager.ts`, and the animation/undo/preset round-trip. The legitimate uses are precisely the per-frame derivations enumerated in path-4 above (`engine-gmt/engine/managers/UniformManager.ts:332-388` for camera basis + `uPixelSizeBase` + env rotation + fog linearisation, `engine-gmt/engine/managers/UniformManager.ts:390-488` for light packing). Cite the source feature uniform (paths 1-3) and have `UniformManager` derive into a BASE slot — the `if (sourceUniform) { … }` guard pattern at `engine-gmt/engine/managers/UniformManager.ts:363-369` is the canonical defensive shape.

R6. **Names MUST follow the prefix convention.** `BASE_SCHEMA` uses short generic names (`uTime`, `uResolution`, `uCameraPosition`, `uPixelSizeBase`); features use themed prefixes (`uPT…` for pathtracer, `uLight…` for lighting, `uModular…` for the modular pipeline, `uWeave…`/`uWs…` for weave, `uEnv…` for materials env, `uFog…` for atmosphere). The *convention* itself is still review-enforced only, but an actual name **collision** now throws at module load — see Invariant I3 below.

R7. **Always add the canonical identifier to `engine/UniformNames.ts` (`Uniforms.X = 'uX'`) and reference it by `Uniforms.X` in the schema entry, NOT a string literal.** Cite: `engine/UniformNames.ts:2-91`. The `UniformName` string-literal union derived at `engine/UniformNames.ts:93` is the typed "valid uniform identifier" check downstream code uses; bypassing it with a raw string defeats it. Note that the section-header comments in `UniformNames.ts` (e.g. `// Environment`) are organisational only — they do NOT correlate with the BASE-vs-feature partition; `EnvRotationMatrix` sits under `// Environment` but is in `BASE_SCHEMA` (see q-031 in `docs/history/doc-audit-state/survey/_followups/q-031.md`).

R8. **For an array-typed slot, default to a typed array (`Float32Array(N)`) or `new Array(N).fill(new THREE.Vector3())`** — `createUniforms` deep-clones `Float32Array` (`new Float32Array(val)` at `engine/UniformSchema.ts:149`) and array-of-Three (`.map(v => v.clone ? v.clone() : v)` at `engine/UniformSchema.ts:148`). A bare-object default like `{ x: 0 }` will pass through as a primitive at `engine/UniformSchema.ts:151` and break array indexing on the shader side. Producer example: `engine-gmt/features/lighting/index.ts:130-140`.

R9. **Do not set `UniformDefinition.comment` expecting any runtime effect.** It is interface-declared at `engine/UniformSchema.ts:34` but has zero consumers: the chunk emitter at `shaders/chunks/uniforms.ts:7-14` reads only `name`, `type`, `arraySize`, `backingOnly`, and the Three.js factory at `engine/UniformSchema.ts:141-155` reads only `name` and `default`. `comment` survives as an inline-doc convention on three `BASE_SCHEMA` entries. The `precision` field this rule also used to cover was **deleted** in `36ad672c` (zero producers, zero consumers); the precision preamble is hard-coded to `precision highp float; precision highp int;` at `shaders/chunks/uniforms.ts:5`. See q-027 in `docs/history/doc-audit-state/survey/_followups/q-027.md`.

R10. **`backingOnly: true` requires a paired feature `inject()` call to `builder.addUniform(name, type, arraySize?)`.** The flag tells the schema walker at `shaders/chunks/uniforms.ts:8` to skip emitting the static GLSL `uniform …;` declaration (the Three.js backing is still created by `createUniforms` at `engine/UniformSchema.ts:141-155`, which does NOT check the flag, and neither `ShaderBuilder.buildUniformsBlock` in engine-core nor its engine-gmt sibling `buildUniformsString` checks it either). To actually use the uniform in GLSL, the feature must add the declaration on demand from its own `inject()` — see `engine-gmt/features/core_math.ts:106-110` for the canonical `'Modular'`-only emission of `uModularParams`. Without the paired `addUniform`, `backingOnly` produces a Three.js slot that no shader can read.

## Invariants

I1. **The shared `BASE_SCHEMA` prefix must stay in sync across both trees.** `engine/UniformSchema.ts:53-102` and `engine-gmt/engine/UniformSchema.ts:35-83` are a Pattern C parametrisation-hook fork (see [`docs/policy/engine-fork-rules.md`](./engine-fork-rules.md)) and carry the same entries in the same order. **They are no longer byte-identical end-to-end**: the engine-gmt copy appends a GMT-only MB3D derived-rotation bank (`engine-gmt/engine/UniformSchema.ts:85-104`) and widens `GLSLType` with `'mat4'` (`:10`) to type it. A change to the *shared prefix* in one tree without the same change in the other silently desyncs the two engines; GMT-only additions belong after the shared prefix (or, preferably, in a feature via path 2/3).

I2. **The `featureRegistry.getUniformDefinitions()` harvester is the single funnel for feature-side uniforms.** Both `extraUniforms` (path 2) and `params.*.uniform` (path 3) feed through `engine/FeatureSystem.ts:689-716`; downstream code in `engine/UniformSchema.ts:104` and `engine-gmt/engine/UniformSchema.ts:107` consumes only the funnel output. New feature-contribution paths MUST extend the funnel, not bypass it.

I3. **Uniform-name collisions THROW at module load.** Since `36ad672c` (2026-05-21) `engine/UniformSchema.ts` runs two checks between the funnel and `UNIFORM_SCHEMA`: feature-vs-base at `engine/UniformSchema.ts:113-120` and feature-vs-feature at `engine/UniformSchema.ts:121-131`. Both throw an `[UniformSchema]` `Error` on first import, naming the offending uniform(s), so the breakage is a boot failure rather than a mysterious wrong-default at render time. The engine-gmt twin carries the same pair at `engine-gmt/engine/UniformSchema.ts:117-136`. `UNIFORM_DEFAULTS`'s last-wins reduce is therefore never reached with a duplicate name. This supersedes the silent-filter behaviour described in q-029 (`docs/history/doc-audit-state/survey/_followups/q-029.md`) — that follow-up predates the fix. Note the checks live in `UniformSchema`, **not** in the harvester: `getUniformDefinitions()` still happily returns duplicates.

I4. **`backingOnly` is declared in `engine/UniformSchema.ts:35-42` and enforced only in `shaders/chunks/uniforms.ts:8` (and the engine-gmt mirror at `engine-gmt/shaders/chunks/uniforms.ts:8`).** No other layer checks the flag. `createUniforms` at `engine/UniformSchema.ts:141-155` and `engine-gmt/engine/UniformSchema.ts:145-159` ignore it, and so does `ShaderBuilder.buildUniformsBlock` (`engine/ShaderBuilder.ts`) — which is by design, since that is the path a feature uses to re-add the declaration under R10. Adding a new enforcement site (e.g. a `UniformManager`-level skip) without coordinating with the chunk emitter will produce inconsistent behaviour. See q-026 in `docs/history/doc-audit-state/survey/_followups/q-026.md`.

I5. **`UniformSchema.ts` triggers `registerFeatures()` at import time** (`engine/UniformSchema.ts:24-25`, `engine-gmt/engine/UniformSchema.ts:7-8`). Any module that imports a **value** from `UniformSchema` (`UNIFORM_SCHEMA`, `UNIFORM_DEFAULTS`, `createUniforms`) fires the side effect. A **type-only** import — `UniformDefinition` — does NOT: with no `verbatimModuleSyntax` in `tsconfig.json`, both tsc and esbuild elide the whole import statement when every imported name is used only in type position. That elision is load-bearing, not incidental: `engine/FeatureSystem.ts` imports `UniformDefinition` from here while this module imports `featureRegistry` from there, so a value-syntax import would make the cycle live and evaluate `UniformSchema` while `featureRegistry` is still in TDZ. Keep the `import type` on `engine/FeatureSystem.ts`. Adding a new contribution path that participates in this top-level pre-build MUST be deterministic and not depend on subsequent imports.

I6. **`UniformManager` is engine-gmt-only.** The engine-core `engine/managers/` directory contains only `ConfigManager.ts`. A new non-GMT app contributing uniforms via path 4 MUST write its own per-frame writer; there is no shared substrate to reuse. Verified at `docs/history/doc-audit-state/survey/_followups/q-099.md:23-25`.

I7. **Sampler defaults are `null`.** Producers using path 1 or path 2 with `type: 'sampler2D'` MUST default `value` to `null` (see `engine/UniformSchema.ts:78,81` for BASE precedent and `engine-gmt/features/lighting/index.ts:143-144` for the env-CDF samplers). Consumers MUST bind a real texture before the first draw or accept undefined-sampler GL behaviour.

I8. **`UniformNames.ts` section headers are non-binding.** The `// Environment`, `// Lighting`, `// Modular` comments at `engine/UniformNames.ts` group identifiers logically but do NOT correlate with the BASE-vs-feature contribution path. `EnvRotationMatrix` and `FogColorLinear` sit under `// Environment` (`engine/UniformNames.ts:53,61`) but are in `BASE_SCHEMA` (`engine/UniformSchema.ts:100-101`), not feature-contributed. See q-031.

## Interactions with other subsystems

- **Registration-side contract** — `FeatureDefinition.extraUniforms` and `ParamConfig.uniform` are introduced in `engine/FeatureSystem.ts` JSDoc (ADR-0012 registry freezing, ADR-0036 `defineFeature`, ADR-0059 capability protocol); `getUniformDefinitions()` is the funnel. - **Engine-core schema surface** — `engine/UniformSchema.ts`, `engine/UniformNames.ts`, `engine/ShaderBuilder.ts` (ADR-0019, ADR-0020) carry it in-source. This doc complements them by enumerating the four contribution paths; archived narrative at `docs/history/audit-2026-05-20/archive/engine/shader-builder.md`.
- **Engine-gmt downstream consumers** — `UniformManager.syncFrame` (per-frame writer), `ConfigManager.update` (uniform-back-fill from CONFIG diffs), and the `engine-gmt/engine/ShaderBuilder.ts` positional assembler that decides which GLSL declarations actually reach the shader (ADRs 0043-0044; see [`.claude/rules/gmt-renderer.md`](../../.claude/rules/gmt-renderer.md)). Path-4 (direct `UniformManager` writes) is exclusively a GMT-side concern. Archived narrative at `docs/history/audit-2026-05-20/archive/engine-gmt/shader-pipeline.md`.
- **`docs/history/audit-2026-05-20/archive/engine/plugins-host.md`** — does not currently contribute uniforms (plugins host owns UI chrome, not the render contract), but the "no uniform plugin contract" carry-in note at `docs/history/doc-audit-state/survey/e07-plugins-host.md:187` is what motivated this doc. Plugin authors who need a uniform should pick a path 1-3 in a feature definition, not invent a fifth.
- **[`docs/policy/engine-fork-rules.md`](./engine-fork-rules.md)** — `UniformSchema.ts` is the canonical Pattern C (parametrisation-hook) exemplar; `UniformNames.ts` is the canonical Pattern A (re-export shim) exemplar; `UniformManager.ts` is the canonical Pattern D (engine-gmt-only) exemplar. R4 above is the uniform-specific application of those patterns.

## Historical context

No existing module doc covered the uniform contribution contract — the surveyor's closing note carried into `docs/history/audit-2026-05-20/archive/engine/plugins-host.md:238` ("no uniform plugin contract") is what motivated this file. The in-source comments that this doc consolidates and that future reformats MUST preserve:

- `engine/UniformSchema.ts:24` — `// Ensure features are registered before schema is built`. The rationale for the eager top-level `registerFeatures()` call that makes I5 load-bearing. The `@invariant` block at `engine/UniformSchema.ts:1-17` spells out the value-import-vs-`import type` distinction and why the elision keeps the `FeatureSystem` cycle benign.
- `engine/UniformSchema.ts:35-42` — `UniformDefinition.backingOnly` JSDoc, now carrying the `@enforcement` tag that closes q-026 / documents R10.
- `engine/UniformSchema.ts:45-52` — `// Base Schema — three categories:` (rewritten from the stale `(Pure Core)` label; matches R3).
- `engine/UniformSchema.ts:96` — `// Optimizations (Shared by Geometry & Lighting)`. The accurate category label for the CPU-derived caches at `engine/UniformSchema.ts:97-101`.
- `engine/UniformSchema.ts:105-112` — the collision-detection rationale comment (`// Collision detection at module-load time. Two failure modes the naming convention alone can't catch…`). This replaced the old `// Deduplicate in case a feature defines a uniform that's also in base` line and is the in-source statement of I3.
- `engine/FeatureSystem.ts:344` — `// extraUniforms: complex uniforms (arrays, structs) that aren't 1:1 with a param entry`. The one-line in-source description of path 2.
- `engine-gmt/features/core_math.ts:60-61` — `// backingOnly: Three.js uniform object always exists for syncModularUniforms(), but GLSL declaration is injected conditionally in inject() only for Modular formula`. The canonical worked example of R10's paired-`addUniform` pattern.

The four-path contract emerged organically across the lifetime of the codebase. Path 1 (BASE_SCHEMA) is the oldest; path 2 (extraUniforms) was added when the lighting feature outgrew the 1:1 binding; path 3 (params.*.uniform) is the DDFS-era preferred path that subsumed most new uniforms; path 4 (UniformManager direct writes) is a render-loop concern that predates the DDFS framing and persists for legitimate per-frame CPU-derivation cases. Future shader-extension work (cf. `plans/mesh-export-unification.md` for one downstream consumer) should pick path 3 by default and treat paths 1-2 as escape hatches gated by the rules above.
