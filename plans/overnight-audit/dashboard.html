B low e02-tick-registry engine/TickRegistry.ts:148

runTicks has no per-handler error isolation: one throwing tick aborts every later phase for that frame, and in app-gmt also aborts the worker dispatch that follows it.

The dispatch loop is a bare `for (let i = 0; i < _entries.length; i++) { _entries[i].fn(delta); }` (engine/TickRegistry.ts:148-150). A tick that throws — say an OVERLAY gizmo hitting a null ref — takes out every tick after it in phase order, and because GmtRendererTickDriver calls runTicks inline before serializing the camera and calling proxy.sendRenderTick (:483), the throw also stops the worker frame dispatch. Since a tick that throws once usually throws every frame, the realistic symptom is a permanently frozen image plus a dead timeline, presenting as 'the renderer hung' rather than 'a gizmo is broken'. This is a design fork, not a defect, which is why it was not acted on. OPTIONS: (a) leave as-is — fail-fast keeps bugs loud, and the current tick set is small and stable; (b) wrap each fn(delta) in try/catch that logs once per tick name and keeps going — the rest of the frame survives and the failing tick is named, at the cost of a try/catch per tick per frame (negligible: 4-8 entries) and the risk of a broken tick going unnoticed in production; (c) (b) plus auto-unregistering a tick after N consecutive throws, which self-heals but can silently drop functionality. RECOMMENDATION: (b), with the catch logging the tick's `name` (the registry already stores it) and warning once per name rather than per frame. It converts the worst failure mode — silent whole-renderer freeze — into a named console error while leaving the failure visible.

B low e02-tick-registry engine/TickRegistry.ts:129

ADR-0003 promises that synthetic-tick and headless harnesses can drive runTicks from their own loop, but the 1 ms double-run guard would silently drop every call in such a loop after the first.

ADR-0003's Context says outright: 'Apps that intentionally use a custom driver (worker-driven, headless test harness) must still be able to call runTicks from their own loop — so the solution can't reject a single legitimate driver, only the second one within a frame.' The implementation cannot distinguish the two cases: TickRegistry.ts:129 suppresses any call arriving less than DOUBLE_RUN_WINDOW_MS = 1 ms after the previous one, regardless of who made it. A frame-stepping harness (offline video export, a deterministic headless test rendering N frames back-to-back) runs each iteration in well under 1 ms and would get exactly one tick then silence — and silently, since the dev warning is one-shot and its text blames a driver double-mount, sending the reader to the wrong place. LATENT, NOT LIVE: only three runTicks call sites exist and none hits it today. It matters now because 4K/offline frame-sequence export is a known roadmap gap, and an exporter is precisely the shape that would trip this. OPTIONS: (a) do nothing and let whoever writes the exporter discover it — cheap now, confusing later; (b) add an opt-out, e.g. an exported setTickGuardEnabled(false) or runTicksUnguarded(delta) that a harness calls explicitly, keeping the guard on for the RAF path; (c) drop the time-window heuristic for driver identity — have drivers claim the registry via a token so a second claimant warns and no-ops while a single claimant can tick as fast as it likes. RECOMMENDATION: (b) now — a few lines, preserves the ADR-0003 guarantee verbatim, does not disturb the RAF path. (c) is the correct long-term shape but is not worth the churn until a second driver kind exists. Either way ADR-0003 wants an Update block noting the gap.
