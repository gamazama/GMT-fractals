# Critic: lighting (GMT-SYSTEMS.md section 4 and table 2.2)

Read-only review, 2026-10-07. Everything below was read in the worktree unless marked unverified.
Nothing was compiled or run.

## Verdict

Section 4 is right about the big shape: the light record is plain data, the UI's renderer coupling
is narrow (a proxy read of `sceneOffset` plus the viewport camera), and the direct-light loop in
`pbr.ts` does separate from the march at exactly two calls (`GetSoftShadow`, `GetAO`). Route A is
sound. Route B is under-described: the "shading half" drags in the miss handler, the fog chain, the
environment sampler and GMT's shadow uniforms, and one row of table 2.2 contradicts it. The Surface
frame is generic in mechanism but has one implementer, and it is not the frame its name suggests.

## What I confirmed

- `engine-gmt/features/lighting/index.ts` imports the GLSL at module top
  (`getShadowsGLSL`, `getLightingPBRSimple/Full`, `LIGHTING_SHARED`, `getPathTracerGLSL`, lines 9-12)
  and the UI imports `getLightFromSlice` from that same file (`LightControls.tsx` line 7,
  `LightPanelControls.tsx` line 12). So L1 (split the list out) is a real precondition, as stated.
- `calculatePBRContribution` (`shaders/chunks/lighting/pbr.ts`, `getLoopOpen`) calls no distance
  function itself. Its only march is
  `float s = GetSoftShadow(shadowRo, shadowL, shK, shadowDist, stochasticSeed, surfEps, epsRate);`.
  The footprint block reads `uCameraPosition + uSceneOffsetLow + uSceneOffsetHigh`, `uCamType`,
  `uPixelSizeBase`, `uPixelThreshold`, `uDetail`, `uInternalScale`, `PRECISION_RATIO_HIGH` - all
  marcher state, as the document says. R2 is correctly identified.
- Falloff packing: `const k = range > 0.001 ? 99.0 / (range * range) : ...`
  (`UniformManager.ts`, light block). sqrt(99) = 9.95, so the "range = 9.95 L" headlamp match holds.
- UI ranges: Range `min={0} max={100} step={0.1}`, position `min={-10} max={10} step={0.01}`
  (`LightControls.tsx` lines 517, 625). A view-unit Range of 40 fits the existing slider.
- `getProxy()` only constructs the proxy object (`WorkerProxy.ts`, `getProxy`); `new Worker(` sits
  further down in an init path (line 178; the enclosing method name was not read - unverified).
  `get sceneOffset() { return this._localOffset; }` returns zeros with no worker. So the four UI
  files will import and render without GMT's worker today; they just compute against a zero offset.

## Findings

### 1. WRONG - table 2.2 "global shadows: ADAPTER, GMT's names are not reused" contradicts route B

`pbr.ts`, inside the light loop:

```
if (calcShadows && uShadows > 0.5 && uLightShadows[i] > 0.5) {
    ...
    float shK = uShadowSoftness;
    ...
    float s = GetSoftShadow(shadowRo, shadowL, shK, shadowDist, stochasticSeed, surfEps, epsRate);
    shadow = mix(1.0, s, uShadowIntensity);
```

and above it `float biasAmount = surfEps * (2.0 + uShadowBias * 500.0);`.

Once pass S is assembled from GMT's chunk (route B), the depth-buffer provider sits behind this
call. It receives `k` = `uShadowSoftness` (GMT Hardness, 2..2000, log), a ray origin already pushed
by `uShadowBias`, a maximum distance of `DIR_LIGHT_DIST` (100.0, `chunks/math.ts`) for directional
lights, and its result is mixed by `uShadowIntensity`, all gated on `uShadows`. The shell's
"Strength, Softness 0.05, Length 0.6" have no path into that function. Either the shell writes its
numbers into GMT's uniform names (the thing the row forbids), or the chunk grows a fourth rework
that R1-R3 do not list.

The same collision is in the UI: `LightPanelControls.tsx` line 446 hard-mounts
`<AutoFeaturePanel featureId="lighting" groupFilter="shadows" />`. Mounting the panel in the shell
shows whatever feature `lighting` declares in group `shadows`. 4.1 promises the shell's three rows
instead of Hardness / Quality / Bias; nothing in L3-L5 changes that line.

Fix: decide it once. Either (a) the shadow section of the panel becomes a slot the app fills, and
the chunk takes a small shadow-parameter struct from the provider side (generic: any shadow
provider declares its own controls), added to stage L and stage B at about 0.5 to 1 session; or
(b) say plainly that after route B the deep zoomer's shadow controls ARE Opacity / Hardness / Bias
re-interpreted, and drop the "names not reused" row.

### 2. MISSING - the shading half is not "surface inputs only": miss handler, fog and environment come with it

`shading.ts`, `getShadingGLSL`, defines these unconditionally above `calculateShading`:

```
vec3 sampleMissEnv(vec3 ro, vec3 rd, float roughness, vec3 throughput) {
    g_missSelfFogCover = 0.0;
    vec3 raw = sampleMiss(ro, rd, roughness, uEnvStrength);
```

`sampleMiss` and `g_missSelfFogCover` are generated by `ShaderBuilder.buildMissHandler`
(`engine-gmt/engine/ShaderBuilder.ts` lines 365-380), and light-sphere code is injected into it via
`addMissLogic` (`lighting/shared.ts` line 84 comment). So an R3 "shading only" build must still emit
the miss handler or the chunk does not compile.

`calculateShading` itself calls `applyEnvFog(GetEnvMap(...))` twice. That chain reads
`uFogIntensity`, `uFogFar`, `uFogTint`, `uFogColorLinear` (atmosphere feature) and, in `env.ts`
`envSampleCore`: `uEnvSource`, `uEnvRotationMatrix`, `uEnvGradient`, `uEnvMapTexture`,
`uEnvAvgColor`, `uEnvMaxMip`, `uUseEnvMap`, `uEnvMapColorSpace`, `applyTextureProfile`. Plus
`uAOColor`, `uRim`, `uRimColor`, `uRimExponent`, `uEnvStrength`, `uReflection`, `uSpecular`,
`uDiffuse`. Table 2.2 files "materials, rim, emission, env ambient, env reflection" as
"AS-IS once route B lands ... need only n, v, albedo, roughness, direction". In GLSL argument terms
yes; in uniform terms it needs the atmosphere, environment (two textures, an average colour computed
at load), AO and materials features installed and their uniforms fed by something that is not
GMT's `UniformManager`. The document flags "how separable UniformManager is" as unverified but
prices this row at 0.

Also, the proposed signature `shadeSurface(p, n, v, albedo, emission, roughness, surfEps, epsRate, seed)`
is short for GMT's own injected reflection block. `features/reflections/index.ts` lines 16-17 list
the variables it expects in scope, including `p_fractal` and `d`, and it uses them:
`length(p_fractal) * PRECISION_RATIO_HIGH` (lines 43, 74, 91) and
`traceReflectionRay(currRo, currRd, d, reflFade)` (line 170). GMT keeps working only if the split
function still carries both. And `epsRate` cannot be an argument as written: it is per light,
`float epsRate = epsRateBase * dot(shadowL, viewDirN);`, computed after the jitter re-aims
`shadowL`. The argument is `epsRateBase`.

Fix: restate R1 as `shadeSurface(p, pAbs, d, n, v, albedo, emission, roughness, surfEps, epsRateBase, seed)`;
add to R3 "the miss handler and env chunk are part of the shading half"; add a line item for the
uniform feed (which features the shell installs, who uploads the env textures). Honest size for
route B: add 1 to 2 sessions to the 6 to 6.5 quoted.

### 3. MISSING - "Environment up = the fitted plane's normal" is not what GMT's chunk does, and route B changes the picture

Route A today (frozen page, `SHADE_FRAG`):
`skyDome(0.5 + 0.5 * dot(n, uPlaneN))` and `skyDome(0.5 + 0.5 * dot(reflect(rd, n), uPlaneN))` -
a hard-coded two-colour dome, up = plane normal.

GMT's chunk (`env.ts`, `envSampleCore`): up is the shading frame's +Y (`float t = dir.y * 0.5 + 0.5`,
`acos(dir.y)`), and the only rotation is `dir.xz = uEnvRotationMatrix * dir.xz` - a turn about Y.
There is no way to tilt the sky to a plane normal short of rotating the whole shading frame so the
plane normal is +Y, which means `n`, `v` and every light direction must be rotated with it by the
caller. Section 4.4's row is true of route A and silently assumed for route B. If the frame is not
plane-aligned after B, the dome light comes from camera-up or world-up and every default view
relights. If it is plane-aligned, a loaded HDR sky visibly rotates in reflections as the plane fit
drifts (the rig "moves toward each fit by a fraction" while flying - page comment above `look`).

Fix: name the shading frame for route B in R2's JSDoc line (plane-aligned, +Y = fitted normal),
state that env maps will swim with the fit, and put "dome and reflection match route A" into the
A/B referee.

### 4. WEAK - `frame: 'surface'` is generic in mechanism, single-consumer in fact, and misnamed

- In GMT the provider "reports `surfaceNormal: null` until it has a plane fit", and the GMT plane fit
  is in the "Later" row (1 to 2 sessions, unscheduled). So stage L ships GMT a third attachment
  option that is disabled for every GMT user indefinitely. That is the capability pattern CLAUDE.md
  asks for, not an `if deep zoom` - but it is a control in GMT that exists for one other app.
- The attachment control is binary in both places today: an anchor icon button with
  `title={light.fixed ? 'Attached to Camera (click to unanchor)' : 'World Anchored (click to attach to camera)'}`
  (`LightControls.tsx` line 412) and a two-entry toggle `{ label: 'Headlamp', value: true }`
  (`LightPanelControls.tsx` line 280). "Becomes a three-way choice" is a redesign of the hover popup's
  icon button, not a relabel; it is not sized.
- The page's Surface placement is not a surface-fixed frame. `rigDir(azDeg, elDeg, right, up)`
  builds the azimuth from the CAMERA's right and up (`ca * right[i] + sa * up[i]`) and only the
  elevation from the plane. A Surface light keeps its elevation above the ground but turns with the
  camera's yaw. 4.1 says it "keeps raking it as he flies and turns" - true - but an owner who reads
  "Surface" beside "World" and "Camera" will expect it to stay put on the surface when he turns.
- `LightParams.rotation` is an Euler applied to (0, 0, -1) in order 'YXZ' (`UniformManager.ts`:
  `this.lightEuler.set(..., 'YXZ')`). The document does not say how azimuth 152 / elevation 40 is
  stored in that Euler, and "default rig reproduces today's frame" depends on it.
- A scene saved with `frame: 'surface'` and opened in GMT falls back to Camera (4.2 item 4). The
  light record stops being portable between the two apps; not stated in 4.4.

Fix: either schedule the GMT plane fit inside stage L so the option has two implementers on the day
it lands, or keep the three-way control but have an unsupported option absent rather than disabled
in GMT until then (owner decision; add to section 8). Describe Surface in 4.1 as "elevation above
the surface, direction in the picture". Specify the Euler mapping.

`lengthUnit: 'view'` is the more genuinely generic of the two: GMT already has a view scale
(`WorkerProxy.lastMeasuredDistance`, the same number the drag-in clamp uses). Unverified: whether
that number is steady enough frame to frame to scale a Range without popping, and whether a change
to it resets accumulation.

### 5. WEAK - L2 and L3 are undercounted

- The packing block is not "light list + view frame in". It adds per-light modulation deltas inline:
  `l.falloff + dFalloff`, `(lp?.x ?? 0) + dX`, `(lr?.x ?? 0) + dRotX` (`UniformManager.ts` lines
  447-480; the deltas are defined above line 440, which I did not read). The pure function needs the
  modulation map as a third input, and the shell must supply it or light modulation and audio-driven
  lights do nothing in the deep zoomer.
- "The same conversion is written five times" lists `handleToggleFixed` twice. I count
  `engine.sceneOffset` reads at `LightControls.tsx` 212, `LightPanelControls.tsx` 131 and 170, and
  `SingleLightGizmo.tsx` 44 and 76 - five UI sites before `VirtualSpace` and `OverlayProjection`
  (the latter two not opened by me). Seven or more, not five. L3's 2 sessions is tight.
- The UI reaches further into GMT's lighting slice than the list: `s.lighting?.renderMode`,
  `s.lighting?.ptAreaLights` and a Sphere-light prompt that writes
  `updates.renderMode = 1.0; updates.ptAreaLights = true` (`LightControls.tsx` 149-150, 437-447);
  `ShadowControls.tsx` reads `shadowsCompile`, `areaLights`, `shadowAlgorithm`. All components read
  `s.lighting` by name, so the shell must register a feature with id `lighting`. `supports.types`
  covers hiding Sphere; nothing covers the path-tracer prompt.

## What the owner will be surprised by at 1e-40

1. Turn the camera and a Surface light turns with it (finding 4).
2. Tick Cast Shadows on a fourth light: nothing happens (cap of 2 to 3, stated in 4.4, but the
   checkbox is per light with no cap in `LightControls.tsx`).
3. The lights lag a flying frame and freeze during a still; an exported still measures the rig
   afresh ("'fresh' ... measured now, blocking"), so the export can be lit slightly differently
   from the frame he was looking at. Page behaviour today, not mentioned in 4.4.
4. After route B the sky no longer follows the ground unless the frame is plane-aligned, and if it
   is, a loaded environment map swims (finding 3).
5. The shadow rows: either GMT's Hardness / Bias with new meanings, or the shell's three - the
   document currently promises both (finding 1).
6. The default key is forced white on the page and fill / kicker carry half of GMT's colour
   (`tint: 0.5`, `fillCol: [1.0, 0.246, 0.0]`). Opening the colour picker on the default rig will
   show colours that are not GMT's #ff8800 / #0088ff.
